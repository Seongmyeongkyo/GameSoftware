                     SimpleGame 프로젝트 기획서 초안 v1
                       (KPU Game Software Engineering)
================================================================================

작성 목적 : 프로젝트의 컨셉·시스템·기술 사양을 한 문서에 정리.
문서 상태 : 초안. 세부 결정 항목(팀 구성, LLM 옵션, 죽음-리스폰 방식 등)은
            챕터 10에 미해결 상태로 유지.
버전     : v1
기반 코드 : Lee Taek Hee 교수님의 SimpleGame 스타터
            (OpenGL 3.0 + freeglut + GLEW + Visual Studio C++)


================================================================================
[1] 개요 (Overview)
================================================================================

1.1 프로젝트 정체성 한 문장
--------------------------------------------------------------------------------
"암울한 무한 중세 세계에서 등가교환의 규칙 아래 살아가는 순례자.
 죽음은 되돌릴 수 있지만 대가는 알 수 없으며,
 세계 어딘가에는 규칙이 공정한 성역이 있다."


1.2 장르 및 시점
--------------------------------------------------------------------------------
장르     : 2.5D 오픈 월드 RPG (프로시저럴 · 창발형)
시점     : 2.5D (세부 스타일 미결 — 쿼터뷰/사이드뷰 원근/HD-2D 중 결정 필요)
플랫폼   : Windows (Visual Studio, x64)
기술 스택: OpenGL 3.0, freeglut, GLEW, C++


1.3 이 프로젝트의 발표 셀링 포인트
--------------------------------------------------------------------------------
"저희 게임은 개발자도 예측하지 못하는 세계입니다."

- 콘텐츠가 아닌 규칙을 설계했다.
- 세계는 시간이 지날수록 스스로 무거워진다.
- 플레이어의 삶과 죽음이 세계의 문법이 된다.

[2] 게임의 의미 (Thematic Purpose)

2.1 중심 주제
--------------------------------------------------------------------------------
이 게임은 세 가지 명제를 시스템 레벨에서 표현하려 한다.

  (A) 등가교환 : 모든 획득에는 대가가 따른다.
  (B) 죽음의 불가지 : 죽음이 무엇을 뺏고 무엇을 남길지 우리는 모른다.
  (C) 세계는 우리보다 크다 : 개발자도 플레이어도 세계 전체를 알 수 없다.

참고 서사 : 강철의 연금술사(등가교환·인간연성 금기)


2.2 왜 이 게임인가
--------------------------------------------------------------------------------
- 대부분의 RPG는 성장·전투·엔딩을 목표로 삼는다.
  이 게임은 "탐험하는 동안 세계가 무엇을 잃고 무엇을 남기는가"를 다룬다.
- 콘텐츠 소비형 게임이 아니라, 플레이 자체가 세계에 흔적을 남기는 구조.
- 학기 프로젝트로서 그래픽 완성도로 승부하지 않는다.
  시스템의 개념적 강도로 인상을 남긴다.


2.3 정서적 목표
--------------------------------------------------------------------------------
- 기본 톤 : 암울, 무거움, 고요, 무기력한 넓이감.
- 예외 순간 : 극히 드물게 오는 마음이 간지러운 발견들.
- 지향 정서 : 절망보다 애수. 공포보다 그리움.
- 참고 톤 : Dark Souls / Signalis / Bloodborne / Journey / Death Stranding.

# 사용자가 명시적으로 확정한 12개 지침

  1. RPG 게임
  2. 2.5D 형태
  3. 배경 시대 : 중세 암흑시대
  4. 분위기 : 암울하지만 가끔 희망을 얻을 수 있는 사회
  5. 오픈 월드
  6. 월드 크기는 무한대 — 지속적으로 커지는 구조
  7. 주제 : 죽음과 등가교환, "우리가 모르는 상황"
  8. 재미 요소 : 개발자도 모르는 숨겨진 장소·아이템·이벤트가 창발
  9. 지속성 원칙 : 한 번 만들어진 창발적 요소는 조건이 사라져도 존속
 10. 대화 시스템 : AI를 통해 지속적으로 업데이트/변화
 11. 정서 설계 : "마음이 간지러운" 미시 이벤트가 필요
 12. 서사 설계 : 난해한 떡밥(다중 해석·미해결)이 존재해야 함

# 위 지침에서 파생된 두 개의 결정적 규칙

 규칙 1 : 죽음-생성 규칙
   - 플레이어 사망 = 새로운 NPC 하나 생성.
   - 그 NPC는 사망 전까지 플레이어의 성격·패턴·감정을 상속한다.
   - "하나의 죽음이 하나의 생명을 만든다."

 규칙 2 : 지속성 원칙의 해석
   - 규칙은 "탄생 조건"이지 "존재 조건"이 아니다.
   - 오브젝트는 태어난 순간 세계에 등록되며,
     이후 조건이 무너져도 사라지지 않는다.

[4] 세계 및 핵심 루프

4.1 세계관 개요
--------------------------------------------------------------------------------
- 배경 : 이름 없는 중세 세계. 문명은 이미 무너졌거나 무너지는 중.
- 형태 : 지평선이 없는 무한한 대지. 걷는 만큼 세계가 새로 생겨난다.
- 규칙 : 이 세계에서는 모든 것에 대가가 있다.
         회복도, 마법도, 죽음마저도 무엇으로부터 대체된다.
- 예외 : 극히 드문 성역. 이곳에서만 등가교환이 투명하고 공정하다.
- 인간연성 : 죽음을 되돌리는 의식은 존재한다. 그러나 대가는 은닉된다.


4.2 핵심 게임 루프
--------------------------------------------------------------------------------

    탐험 --> 자원·기억 수집 --> 등가교환으로 스킬/장비 획득
      ^                                                |
      |                                                v
   순례 계속 <-- 세계에 흔적 축적 <-- 위기·죽음 --> 새 NPC로 세계 어딘가에 남음
      ^                                                |
      |                                                v
      +-------- 성역을 찾기 위한 더 먼 탐험 <-----------+

- 명확한 엔딩 없음. 세계는 무한이므로 게임에는 "완주"라는 개념이 없다.
- 최상위 목표는 "성역의 발견"이지만, 이 목표조차 필수가 아니다.


4.3 세계관 × 메커닉 매핑 표
--------------------------------------------------------------------------------
| 세계관              | 메커닉 구현                                          |
|---------------------|------------------------------------------------------|
| 등가교환            | 크래프팅·마법·회복이 자원/HP/수명/기억/지형을 소모  |
| 죽음의 불가지       | 대가는 사용 후에야 드러남 (HiddenState)              |
| 우리가 모르는 상황  | 아이템 툴팁 불완전, 저널 미완성, 크립틱 언어         |
| 암울 × 희망         | 대부분 어두운 바이옴, 극소수 확률로 성역 청크        |
| 무한 성장           | 청크 무한 생성 + 플레이어 흔적 영구 누적             |


================================================================================
[5] 핵심 시스템 (5매니저 아키텍처)
================================================================================

이 게임의 심장은 다섯 개의 매니저와 그 사이의 데이터 흐름이다.
각 매니저는 독립적으로 프로토타이핑 가능하도록 설계한다.


5.1 ChunkStreamer — 무한 월드 스트리밍
--------------------------------------------------------------------------------
역할  : 청크 로드/언로드, 결정론적 노이즈 지형 생성, ChunkDelta 관리.
좌표계: Floating Origin (int64 청크 인덱스 + float 청크 상대좌표).
생성  : chunkGen(worldSeed, X, Y) — 항상 같은 좌표는 같은 결과.
층위  : 대륙 노이즈, 지역 노이즈, 세부 지형 노이즈 (계층적).
저장  : 플레이어 수정분만 델타로 저장, 원본 지형은 시드로 재생성.


5.2 RuleEngine — 창발적 콘텐츠 생성
--------------------------------------------------------------------------------
역할  : 청크 생성 시 규칙 평가 → PersistentEntity 생성.
원리  : 규칙은 "탄생 조건"이지 "존재 조건"이 아님.
       한 번 발동한 규칙은 그 청크에서 재발동하지 않음.
구성  : GenerationRule = { conditions[], onSatisfied, probability }
서브  : Grammar Composer — 아이템·이름·구조의 문법 조립기.
        예 : [원소]+[처리]+[의도]+[접두]+[영혼 각인]
             = 정련된 별빛 검, 부서진 재의 부적, ...
발생  : 청크 로드 시 아직 발동되지 않은 규칙만 평가.


5.3 WorldChronicle — 영속 저장소
--------------------------------------------------------------------------------
역할  : 창발체·NPC·대화·관계의 영구 저장.
       세이브 파일이 곧 "세계의 연대기".
자료구조 :
  struct PersistentEntity {
      EntityId id;
      Vec2 worldPos;
      EntityKind kind;   // HIDDEN_PLACE / EMERGENT_ITEM /
                         // EVENT_MEMORIAL / NPC
      RuleId birthRule;
      uint64_t birthTimeMs;
      Blob payload;
  };
저장 정책 (미결) :
  (A) 완전 지속        — 모든 것 영원. 세이브 파일 성장 감내.
  (B) 감쇠 지속        — 특별한 것만 영원, 흔한 것은 시간에 잊혀짐.
  (C) 이벤트 로그 재구성 — 로그만 저장, 로드 시 리플레이.
권장 : (A) 원칙 + 크기 문제 시 (B) 폴백.


5.4 PlayerProfile & NPCFactory — 죽음-생성 파이프라인
--------------------------------------------------------------------------------
역할  : 플레이어 행동 관측 → 특성 벡터 갱신 → 죽음 시 NPCSoul 생성.

관측 지표 :
  성격 (Trait)   : aggression, generosity, curiosity, cruelty
  패턴 (Habit)   : nomad↔settled, explorer↔hoarder, melee↔ranged,
                   biomeStay 편향
  감정 (Emotion) : panic-prone (입력 엔트로피),
                   patient (UI 체류 시간),
                   attached (같은 NPC 재방문),
                   restless (평균 이동 속도)

갱신 방식 : EMA(지수이동평균), alpha 0.02~0.05로 완만하게.

죽음 시 :
  DeathSnapshot 생성 → NPCSoul 응결 → WorldChronicle 등록.
  NPC는 벡터로 튜닝되는 범용 행동 트리 하나만 사용.

행동 트리 파라미터화 예 :
  [전투 진입] weight = f(aggression, caution, panic)
  [NPC 대화]  weight = curiosity + generosity
  [강탈]      weight = aggression - generosity
  [무시]      weight = 1 - curiosity


5.5 DialogueEngine — AI 대화
--------------------------------------------------------------------------------
역할  : LLM 프롬프트 조립 및 응답 → DialogueMemory 갱신.

자료구조 :
  struct DialogueMemory {
      vector<DialogueTurn> history;
      HashMap<TopicId, float> feelings;
      uint64_t lastMetMs;
      uint32_t totalMeets;
      float relationship;   // -1 ~ +1
  };

프롬프트 조립 요소 :
  1. NPC의 특성 벡터 → 문체·성향·말투 문장으로 번역
  2. DialogueMemory → 관계 이력·주제별 감정
  3. WorldContext → 이 NPC가 알 만한 세계 사건
  4. PlayerContext → 플레이어의 현재 프로필·소지품
  5. 활성 MysteryThread → 자연스럽게 흘릴 힌트

지속성 : LLM 응답은 생성 순간 문자열 그대로 DialogueMemory에 저장.
       동일 대사가 재생성되지 않음. 곧 "그때 그 말"이 확정됨.

LLM 옵션 (미결) :
  (A) 외부 API (Anthropic/OpenAI/Gemini)  — 품질 최고, 지연·비용 있음.
  (B) 로컬 LLM (llama.cpp)                — 오프라인, 모델 크기 문제.
  (C) Grammar + LLM 하이브리드            — Grammar가 폴백.
권장 : (A) API 기본 + (C) Grammar 폴백.


5.6 특수 층위 — PoignantEventEngine
--------------------------------------------------------------------------------
역할  : "마음이 간지러운" 미시 이벤트 발생.
특성  :
  - 유일하게 등가교환이 없는 시스템 (대가 없이 오는 것).
  - 알림·UI 없음. 목격만이 상호작용.
  - 3~10초 마이크로모먼트.
  - 확률적으로 매우 낮음.
  - 여파(놓인 꽃, 발자국)는 PersistentEntity로 남음.

원형 카탈로그 :
  - 이전 인격 조우 (자기가 잃었던 아이템을 목에 건 NPC)
  - 흘려진 이야기 (조각난 편지, 반쯤 들리는 대화)
  - 자연 속 침묵 (반딧불이, 배경음의 순간 소거)
  - 시간의 사소한 배신 (죽은 자의 노래를 다른 자가 흥얼거림)

성역과의 결합 : 성역 근처에서 발생 빈도 급증.
              성역 안은 이런 순간들로 가득함.
              성역의 "왜 특별한가"에 대한 정서적 이유가 됨.


5.7 특수 층위 — MysteryRegistry
--------------------------------------------------------------------------------
역할  : 난해한 떡밥(서사 미해결의 실타래)의 조각 분포.

자료구조 :
  struct MysteryThread {
      string id;
      string description;        // 개발자 내부용
      string answer;             // 비워두면 미해결 확정
      vector<Fragment> fragments;
      float distributionSparsity;
      bool leakToDialogue = true;
  };

떡밥의 4가지 층위 :
  세계관 떡밥 : 정체불명의 이름, 하늘 끝 탑, 규칙을 세운 자
  개인 떡밥   : 자신의 이름이 이미 새겨진 무덤, "돌아왔군"
  메타 떡밥   : LLM이 드물게 4th wall을 살짝 건드림
  우주론 떡밥 : 얼굴 없는 자, 눈을 감고 있는 자

큐레이션 vs 창발 :
  - 큐레이션 모드 : 개발자가 손으로 심는 백본 미스터리
  - 창발 모드    : 규칙·NPC·LLM이 우발적으로 만드는 미스터리
  - 플레이어는 둘을 구분하지 못하는 것이 목표

설계 원칙 :
  1. 개발자도 답을 정하지 않는 떡밥이 있다.
  2. 최소 3중 해석이 가능해야 한다.
  3. 미해결은 미해결로 남는다 (엔딩 컷씬 없음).
  4. 놓치는 것이 대다수여야 한다.
  5. 답 있음 : 미해결 = 6 : 4 권장.

선택 :
- SQLite                           : Chronicle 저장 (규모 커지면)
- FastNoiseLite                    : 결정론적 노이즈
- llama.cpp                        : 로컬 LLM 옵션


7.3 렌더링 파이프라인 (목표)
--------------------------------------------------------------------------------
현재 : 단색 사각형 하나 그리는 최소 파이프라인.

목표 스택 :
  1. Sprite Shader     : 텍스처 + UV + 색상 변조
  2. Camera            : View·Projection 매트릭스 (u_Trans 대체)
  3. Tilemap Renderer  : 타일 청크 배치 렌더
  4. YSort Renderer    : 2.5D 깊이감을 위한 스프라이트 정렬
  5. Postprocess FBO   : 톤 매핑, 비네트, 컬러 그레이딩
                         청크 delta에 따라 채도·명도 하강

셰이더 목록 (예상) :
  SolidRect.vs/fs      : (기존)
  Sprite.vs/fs         : 텍스처 스프라이트
  Tilemap.vs/fs        : 타일 인스턴싱
  Postprocess.vs/fs    : 비네트·톤


7.4 좌표계 및 정밀도
--------------------------------------------------------------------------------
- 월드 좌표     : { int64 chunkX, int64 chunkY, float localX, float localY }
- 카메라 좌표   : float (플레이어 청크 기준 상대)
- 렌더 시 : Floating Origin — 매 프레임 플레이어 청크를 원점으로.
- 이유    : float 정밀도가 대좌표에서 무너짐. 무한 월드에서 필수.


7.5 저장 포맷
--------------------------------------------------------------------------------
초기 : JSON 파일 트리
  save/
    world.json           # worldSeed, worldClock
    chunks/
      delta_X_Y.json     # 청크별 델타
      rulesFired_X_Y.json# 청크별 이미 발동한 규칙
    entities/
      persistent.json    # WorldChronicle 전체
    dialogues/
      npc_<id>.json      # NPC별 대화 이력
    player/
      profile.json       # 현재 특성 벡터

향후 규모 커지면 SQLite로 이관.


7.6 LLM 통합 사양
--------------------------------------------------------------------------------
- 프로토콜        : HTTPS + JSON
- 인증           : 환경 변수 API key (코드 하드코딩 금지)
- 요청 크기       : 시스템 프롬프트 ~1500 토큰, 유저 입력 ~200 토큰
- 응답 크기       : 60~200 토큰 (짧게)
- 타임아웃       : 5~10초, 초과 시 Grammar 폴백
- 캐싱           : DialogueMemory에 영구 저장 (지속성 원칙)
- 비용 관리       : 학기 시연 규모에선 수천 원 예상
- 오프라인 모드    : Grammar Composer가 완전 대체 (열화 대응)


7.7 성능 목표
--------------------------------------------------------------------------------
- 프레임      : 60fps @ 500x500 (스타터 창 크기)
- 청크 크기   : 32×32 타일 (조정 가능)
- 활성 청크   : 카메라 주변 5×5 (총 25개)
- NPC 시뮬레이션 : 시야 안 실시간 + 원거리 배치 업데이트
- 청크 로드   : 백그라운드 스레드에서 (메인 스레드 블록 금지)


7.8 규칙 엔진 사양
--------------------------------------------------------------------------------
- 규칙 저장 : JSON 정의 파일 (rules.json)
- 규칙 예시 :
  {
    "id": "chapel_of_forgotten_stars",
    "conditions": [
      {"type": "noise_gt", "layer": "altitude", "value": 0.7},
      {"type": "noise_lt", "layer": "humidity", "value": 0.2},
      {"type": "chunk_mod", "value": 137, "expected": 0},
      {"type": "nearby_graves_min", "radius": 8, "count": 3},
      {"type": "time_range", "start": "00:00", "end": "03:00"}
    ],
    "spawns": [
      {"kind": "HIDDEN_PLACE", "template": "chapel"}
    ],
    "probability": 1.0
  }

9. 콘솔 대화 세션 성공      — "이전 인격에서 태어난 NPC와 대화"
10. PoignantEventEngine 스텁 — 원형 3개

[11] 발표 및 시연 정체성
================================================================================

이 프로젝트는 "저희가 만든 게임"이 아니라
"저희가 만든 게임을 우리도 몰라요"의 발표가 되어야 한다.

발표 요지 :
- 우리 팀은 콘텐츠가 아니라 규칙을 설계했다.
- 세계는 플레이어가 살아갈수록 무거워진다.
- 개발자도 예측할 수 없는 이야기가 매번 발생한다.
- 이 발표에서 우리가 시연하는 세계는, 우리도 오늘 처음 본다.

이 문구가 실제 시연으로 성립되도록 Phase 1을 완성하는 것이 최우선.
